# Olist 全漏斗作品集升级设计

日期：2026-09-25  
状态：待用户确认后实施

## 1. 目标与完成标准

将现有“8,000 条 MQL → 842 条成交”的营销漏斗案例升级为可复算的：

`MQL → 成交 → 卖家 → 首次线索后 90 天内实现的订单与 GMV`

Done = 使用 Olist 官方营销漏斗与 10 万订单数据，公开一套可从原始 CSV 重跑的 Python + SQLite SQL 分析；网页、README、指标文件和自动化测试使用同一口径；所有关键数字通过交叉核验；清楚披露数据、归因、观察期和 AI 协作边界。

## 2. 方案比较与选择

### A. 只润色现有两表漏斗

成本最低，但分析深度仍停留在渠道成交率，不能回答成交后的卖家价值。拒绝。

### B. 接入完整电商数据，分析公平观察窗内的下游价值（采用）

保留现有可解释漏斗，连接 `seller_id` 后增加成交后 90 天订单数和商品 GMV。技术深度、业务意义和面试可讲性较平衡。

### C. 复刻高热度 Kaggle 笔记本的广泛 EDA、聚类和回归

展示内容多，但容易成为“改名复刻”，且物流、评价、卖家价值混在一起会扩大归因错误。只将公开作品用于结构对标，不复制代码与结论。

## 4. 分析范围

### 4.1 核心指标

1. **MQL 数**：指定线索期首次进入漏斗的 `mql_id` 数。
2. **成交数与转化率**：MQL 是否关联到 closed deal；分母始终保留未成交 MQL。
3. **可映射成交率**：closed deal 中 `seller_id` 非空且能匹配卖家表的比例，单独披露，不静默删除。
4. **90 天激活卖家率**：首次线索日起 0—89 天内完成成交且至少产生一个符合口径订单的卖家 / 对应完整观察期 MQL。
5. **90-day orders**：从 `first_contact_date` 起 0—89 天内、且不早于 `won_date` 的有效订单数。
6. **90-day GMV**：同一窗口内该卖家订单商品行的 `price` 合计；不含运费，不等于 Olist 收入、利润、CAC、ROI 或完整 LTV。
7. **90-day GMV per MQL**：某渠道完整观察期 MQL 的 90-day GMV 合计 / 该渠道 MQL 数；未成交、成交但缺 `seller_id`、无订单线索均按 0 贡献处理，避免只看成功者。

### 4.2 公平观察窗

- 观察截止日由订单数据的最大购买时间动态得到。
- 只有 `first_contact_date <= 截止日 - 90天` 的 MQL 进入90天渠道价值比较；所有入选线索拥有相同观察长度。
- 订单必须同时满足 `order_purchase_timestamp >= won_date`、`order_purchase_timestamp >= first_contact_date`、`order_purchase_timestamp < first_contact_date + 90天`。
- 页面披露因观察期不足被排除的 MQL 数及比例；不把它们当成0。
- 营销转化率仍以原固定线索期全部 MQL 为分母，不因下游数据缺失而改变。

### 4.3 有效订单口径

- 主口径使用已交付订单 `order_status = delivered`。
- 商品 GMV 使用 `order_items.price`；`freight_value` 单独保留但不计入主 GMV。
- 同一订单多个商品行按行计 GMV，订单数按 `order_id` 去重。
- 同一订单若包含多个卖家，只把各自商品行归给对应 `seller_id`；不把整单金额复制给每个卖家。

### 4.4 暂不纳入

- 不计算广告成本、CAC、ROI、利润或真实增量效果。
- 不把评论分数直接归因给某个卖家，因为多卖家订单存在归因歧义。
- 不做预测模型、聚类或复杂数据仓库；这些不服务当前实习作品集的核心问题。
- 不直接给出“增加/削减某渠道预算”的确定性建议，只提出待验证假设和实验方案。

## 5. 数据质量与边界检查

分析前必须输出并测试：

- 每张表的行数、列数、主键重复、关键字段缺失；
- `mql_id` 在两张营销表中的唯一性与匹配率；
- `seller_id` 在 closed deals 中的缺失、重复和卖家表匹配率；
- `won_date` 早于 `first_contact_date` 的异常；
- 订单购买时间早于卖家成交时间的记录；
- 订单与商品行匹配率、重复 `order_id + order_item_id`；
- 多卖家订单数量，防止订单金额跨卖家重复；
- 以首次线索日为锚点的90天观察窗完整与不完整样本数量；
- 卖家在 `won_date` 前已经出现订单的记录，单列审计且不计入下游价值；
- 每个渠道样本量，低样本渠道只展示，不做强结论。

### 6.1 仓库必须呈现的完整分析流程

作品集不能只展示结果，仓库和网页应让审阅者按以下顺序追溯：

1. **业务背景与问题定义**：Olist是什么、营销漏斗如何运作、为什么要同时看转化和成交后价值。
2. **数据来源与授权**：官方页面、下载入口、数据时间范围、匿名抽样属性、许可和不可代表的总体。
3. **数据资产清单**：使用哪些CSV、每张表的shape、主键、外键、粒度和作用。
4. **数据模型**：用关系图说明 `mql_id`、`seller_id`、`order_id` 如何把线索、成交、卖家、订单和商品行连接起来，并明确90天窗口从首次线索日开始。
5. **质量审计**：重复键、缺失键、未匹配记录、异常日期、多卖家订单、右删失和渠道样本量。
6. **清洗与口径**：日期解析、缺失渠道单列、订单状态、90天窗口、商品GMV、去重和零值保留规则。
7. **指标字典**：每个指标给业务含义、公式、分子、分母、粒度、时间窗和不能如何解释。
8. **分析实现**：Python完成数据处理和指标产出，SQL独立重算核心指标；代码不是只贴最终结果。
9. **验证记录**：Python/SQL一致性、关键恒等式、边界测试和真实数据运行结果均可查看。
10. **可视化与发现**：图表、样本量、观察期和结论放在一起；每张图对应一个明确问题。
11. **业务建议**：只提出由数据支持的分层验证、埋点治理和实验方向，同时给出优先级和验证指标。
12. **限制与下一步**：成本缺失、观察性数据、归因限制、样本偏差、时间截止和外推范围。
13. **AI协作与本人责任**：具体写明Codex做了什么、本人需要理解和验收什么，不用模糊的“AI赋能”。
14. **复现指南**：环境、下载、目录、PowerShell命令、预期输出、测试命令和常见错误。

新增内容放在现有渠道转化之后。页面至少保留/新增以下四张可复算图，每张只回答一个问题：

1. **渠道转化率横向条形图（保留并强化）**：比较主渠道的 MQL 数、成交数与转化率，条末显示样本量。
2. **全漏斗流程图（新增）**：依次展示完整90天观察MQL、成交、可映射卖家、90天激活卖家；每一步显示人数与相对上一步的保留率，直接暴露流失和数据覆盖。
3. **渠道“转化率 × 90-day GMV/MQL”气泡图（新增主图）**：横轴为 MQL 转化率，纵轴为90天GMV/MQL，气泡大小代表MQL数；`unknown`、缺失和低样本渠道使用警示样式，不与可投放渠道混为一谈。

## 10. 风险与降级方案

- 若无法下载完整电商数据：保持现有公开版本不被破坏，报告阻塞，不生成虚构下游指标。
- 若 seller 映射率或完整观察样本过低：仍如实展示覆盖率，必要时将90天指标降为探索性附录。
- 若不同实现产生不一致结果：停止页面更新，先定位粒度、重复JOIN、订单状态和时间窗口问题。
- 若网页篇幅过长：保留全漏斗核心结论，把详细渠道表折叠；不删除口径与限制。
