# 指标口径与分析方法

## 1. 分析单位

所有渠道比较先压到**每条 MQL 一行**。这保证未成交、已成交但不可映射、可映射但没有订单的线索都留在分母中，不会因为 INNER JOIN 被删除。

## 2. 可完整观察的 MQL

订单样本最晚购买时间为 `observation_end`。一条 MQL 只有在以下条件成立时才进入 90 天价值分析：

```text
first_contact_date + 90 天 <= observation_end
```

不完整观察的 MQL 应排除，而不是当成 0。当前数据中 8,000 条 MQL 均拥有完整 90 天窗口；代码和单元测试仍保留右删失处理，以防数据更新后条件变化。

## 3. 有效订单商品行

商品行同时满足以下条件才计入：

```text
order_status = delivered
order_purchase_timestamp >= won_date
order_purchase_timestamp >= first_contact_date
order_purchase_timestamp < first_contact_date + 90 天
```

窗口采用左闭右开 `[0, 90)`：第 89 天计入，第 90 天不计入。成交前订单不归因给这条营销线索。GMV 在订单商品行上求和；订单数按 `order_id` 去重。

## 4. 核心公式

设同一渠道完整观察的 MQL 数为 `N`：

- 成交率 = 成交 MQL 数 / `N`
- 成交商家可观测率 = 能映射到 sellers 的成交商家数 / 成交 MQL 数
- 90 天激活率 = 90 天内至少有 1 个有效订单的商家数 / `N`
- 90 天订单/MQL = 有效订单去重数 / `N`
- 90 天可观测 GMV/MQL = 有效商品行 `price` 之和 / `N`

所有没有成交、没有商家映射或没有有效订单的**完整观察 MQL**，订单与 GMV 都显式填 0。这样渠道分母不会只剩“成功者”。

## 5. 渠道比较窗口

渠道横向比较固定使用 2018-01-01 至 2018-04-30 的首次接触线索，避免不同渠道因月份构成不同而直接混比。`unknown` 和 `(missing)` 独立展示，但不进入可执行渠道建议；样本数少于 150 的渠道标记为小样本。

## 6. Python 与 SQL 双重实现

- `analysis.py`：检查主键和外键、构造 MQL 级价值表、输出 `data/metrics.js`。
- `queries.sql`：SQLite 用独立 CTE 在相同粒度重算 6 组结果。
- `verify.py`：逐项比较 Python 与 SQL 的计数、比例和金额；任一不一致即失败。
- `test_analysis.py`：使用合成数据覆盖第 89/90 天边界、取消订单、成交前订单、多商品、多商家、零值保留、重复键、坏日期和不完整窗口。

## 7. 如何解释结果

结果只能支持“哪个渠道值得进一步验证”，不能直接支持“给哪个渠道加预算”。原因包括：

- 缺少渠道花费，无法计算 CAC 和 ROI。
- `price` 是商品成交额，不是净收入或利润。
- 只观察 90 天，不是完整 LTV。
- 462 个成交商家不在公开订单样本中，下游价值存在覆盖偏差。
- 历史渠道分配不是随机实验，渠道间客户、月份、商家类型可能不同。

合理下一步是补充渠道成本、统一归因规则、检查不可映射商家的结构，并对付费搜索与自然搜索设计增量实验或准实验，而不是把观察差异当作因果关系。
